# Week 5 Observations

## Task 1 · Subnets and Longest-Prefix Match

- **/31·/32 처리**: /31은 RFC 3021을 따라 두 주소를 모두 사용 가능(first=net, last=net+1), 브로드캐스트는 `None`으로 반환했다. /32는 그 주소 하나가 유일한 호스트(first=last=net)이고 브로드캐스트는 `None`이다 — 네트워크/브로드캐스트를 빼면 주소가 남지 않는 점대점 링크에서 주소 낭비를 막기 위해서다.
- **10.20.30.70의 네 매치**: `10.0.0.0/8`(campus), `10.20.0.0/16`(eng-building), `10.20.30.0/24`(lab-floor), `10.20.30.64/26`(lab-rack-2)에 모두 포함되고(+ `0.0.0.0/0`), longest-prefix match 규칙이 가장 구체적인 /26 → `lab-rack-2`를 골랐다.
- **같은 길이 충돌**: (network, prefix_len)을 dict 키로 저장해 같은 prefix가 다시 추가되면 나중 값이 덮어쓴다(route update). 한 prefix가 두 next hop을 갖는 상태 자체를 허용하지 않는다.

## Task 2 · Where Exactly Are You?

- **NAT 개수**: 캠퍼스(사설 `172.16.31.146` → 공인 `163.152.233.31`)와 집(사설 `192.168.219.100` → 공인 `125.184.80.252`) 모두 NAT 1단이다. tracert에서 사설 홉 바로 뒤 공인 주소 대역(`163.152.233.129`, `125.184.80.129`)이 나오고 100.64/10(CGN)이 없다.
- **두 네트워크 비교**: 캠퍼스 → 집으로 옮기자 사설 주소·게이트웨이(172.16.31.1 → 192.168.219.1)와 공인 주소가 모두 바뀌었고 마스크(/24)만 같았다. 사설 주소는 각 네트워크 DHCP가 독립적으로 주고, 공인 주소는 NAT 장비가 속한 기관/ISP 블록에서 오기 때문이다.
- **Discover 출발지**: 공식 trace에서 `0.0.0.0:68 → 255.255.255.255:67`이다. 주소를 받기 전이라 쓸 수 있는 출발지는 0.0.0.0뿐이고 서버도 모르니 브로드캐스트해야 하며, lease는 86,400초(1일)였다.

## Task 3 · Make Longest-Prefix Match Fast

- **구조와 메모리**: prefix 길이별 dict(`{len: {network: hop}}`)를 두고 긴 길이부터 마스킹·조회해 첫 히트에서 멈춘다. 메모리는 경로당 dict 엔트리 1개 + 사용 중인 길이 목록(여기선 7개)뿐이다. 결과는 20,000개 답 모두 일치, **1591배**(strong)였다.
- **R5 — lookup 비용**: 테이블 크기(5,000)와 무관하게 **테이블에 존재하는 서로 다른 prefix 길이 수**(최대 33, 여기선 7)에 비례하는 해시 조회 횟수로 제한된다.
- **왜 하드웨어는 bit-walk인가**: Python에선 C로 구현된 dict 조회 몇 번이 인터프리터로 32번 노드를 따라가는 것보다 빠르지만, 하드웨어에선 해시 충돌 없이 최악 시간이 주소 폭(32비트)으로 결정적으로 고정되고 파이프라인·TCAM 병렬화가 쉬운 trie가 선로 속도(line rate)를 보장한다.
