집의 NAT 근거: `tracert -d 8.8.8.8` 1홉 `192.168.219.1`(공유기) → 2홉 `125.184.80.129`(공인, 내 공인
주소와 같은 대역). 사설→공인 경계가 공유기 한 번뿐이다. 3홉 이후 `10.x`·`100.107.x`는 공인 구간 뒤 ISP
내부 라우터 주소일 뿐이고, 외부가 본 주소가 이미 공유기 WAN 대역이므로 CGN이 아니다.

**B3** — 캠퍼스 ↔ 집: **공인 주소가 바뀌었다**(163.152.233.31 → 125.184.80.252). 공인 주소는 NAT 장비의
WAN 쪽, 즉 내가 붙은 기관/ISP가 소유한 블록에서 오기 때문에 네트워크를 옮기면 반드시 바뀐다.
**사설 주소도 바뀌었다**(172.16.31.146 → 192.168.219.100). 사설 주소는 각 네트워크의 DHCP 서버(캠퍼스
relay 너머 서버, 집 공유기)가 자기 사설 대역에서 임대해 주는 값이라 네트워크마다 독립적이다 — 우연히 두
네트워크가 같은 사설 주소를 줘도 NAT 뒤라 충돌하지 않는다.
Docker 컨테이너는 반대 사례다: 사설 주소는 바뀌었지만 공인 주소는 캠퍼스와 같다. NAT가 2단이어도 외부에선
1단과 구분되지 않으므로, NAT 단수는 공인 주소가 아니라 경로(tracert)와 주소 대역으로 판단해야 한다.

## Part C · DHCP (경로 B — 공식 trace)

직접 캡처는 하지 못했다(Wireshark 미설치, Wi-Fi 재연결 시 세션 단절). `out/dhcp.pcapng`는 교재 공식
`dhcp-wireshark-trace1-1.pcapng`이다.

| 프레임 | 메시지 | src → dst |
|---|---|---|
| 5, 9 | Discover | 0.0.0.0:68 → 255.255.255.255:67 |
| 12, 13 | Offer | 192.168.86.1:67 → 192.168.86.65:68 |
| 16 | Request | 0.0.0.0:68 → 255.255.255.255:67 |
| 17 | Ack | 192.168.86.1:67 → 192.168.86.65:68 |

- **C2** — Discover의 출발지는 `0.0.0.0`, 목적지는 `255.255.255.255`. 클라이언트는 아직 주소가 없으니
  "이 호스트"를 뜻하는 0.0.0.0 외에 쓸 수 있는 값이 없고, DHCP 서버 주소도 모르니 링크 전체
  브로드캐스트로 보낼 수밖에 없다. 클라이언트는 chaddr(MAC `78:4f:43:98:d9:27`)와 트랜잭션 ID
  `0x56f415ed`로 식별된다.
- **C3** — 서버가 제시한 lease time은 **86,400초(1일)**, T1 renewal 43,200초, T2 rebinding 75,600초.
  (Discover에는 클라이언트가 요청한 7,776,000초(90일)가 있었지만 서버는 1일로 줄였다.)
- **C4** — Offer/Ack는 브로드캐스트가 아니라 `192.168.86.65`와 클라이언트 MAC으로 유니캐스트되었다
  (broadcast flag = 0). Offer 시점에 서버가 yiaddr을 정했고, 클라이언트가 broadcast flag를 끈 채
  "주소 설정 전에도 유니캐스트를 받을 수 있다"고 알렸기 때문에 서버가 MAC을 알고 직접 보낼 수 있다.
- **경로 B 추가** — 임대는 1일. 절반(T1 = 12시간)이 되면 클라이언트는 같은 서버에 **유니캐스트** Request로
  갱신을 시도하고, 실패하면 T2(87.5%, 21시간)에 브로드캐스트로 아무 서버에나 rebinding을 시도한다.
